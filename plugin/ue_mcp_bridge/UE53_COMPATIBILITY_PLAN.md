# UE 5.3.2 Compatibility Plan

## Goal

Restore the UE-MCP functionality that is applicable to Unreal Engine 5.3.2,
without changing the UE 5.4+ implementation or advertising unsupported actions.

The current local target is:

```text
D:\Unreal Projects\VELUX_Design_Studio\VELUX_Design_Studio.uproject
```

The compatibility module is `UE_MCP_Bridge53`. It currently provides the
Blueprint inspection and validation path needed for this project.

## Operating Rules

- Keep all work local unless explicit approval is given to commit or publish.
- Deploy through `src/deploy-cli.ts`; do not hand-copy plugin files.
- Build only against the VELUX UE 5.3.2 editor.
- Do not run mutation smoke tests against VELUX. Use `tests/ue_mcp` for
  destructive coverage after it has a compatible UE 5.3.2 setup.
- Preserve the UE 5.4+ module and its behavior. UE 5.3 support belongs behind
  version gates or in the dedicated compatibility module.
- Mark an action unsupported only after recording the engine API or plugin
  dependency that prevents a safe implementation.

## Completion Criteria

- The module builds and loads in UE 5.3.2.
- Every UE-MCP action is classified as supported, adapted, unsupported, or
  not applicable to UE 5.3.2.
- Every supported or adapted action is registered, documented by its TypeScript
  schema, and has a matching C++ parameter contract.
- Read and validation actions have live coverage against the VELUX project.
- Mutating actions have coverage only in the dedicated test project.
- `project(get_status)` reports the expected VELUX editor before every live
  operation.

## Work Items

### 1. Establish the 5.4 Baseline

- Generate a machine-readable inventory from `ALL_TOOLS` and the C++ handler
  registrations.
- Record category, action, source handler, required module, and whether the
  action mutates editor state.
- Compare the inventory to the UE 5.3 module's registered surface.
- Deliverable: `ue53-action-matrix.json` generated by a script, not maintained
  by hand.
- Exit condition: every advertised action has one inventory record.

### 2. Define Compatibility Boundaries

- Classify each missing action as `portable`, `api-adaptation`,
  `optional-plugin`, `not-applicable`, or `unsupported`.
- Record exact compile errors, unavailable engine APIs, and unavailable plugins
  for nonportable actions.
- Prefer runtime plugin checks for optional features rather than build-time
  dependencies when UE 5.3 can run without them.
- Exit condition: every matrix row has a classification and owner phase.

### 3. Stabilize the Shared Core

- Separate common bridge lifecycle, request dispatch, JSON serialization, and
  handler utilities from UE-version-specific registrations.
- Replace UE 5.4-only container iterator calls with version-safe helpers.
- Keep compatibility wrappers small and centralized.
- Remove direct inclusion of broad handler translation units where a focused
  source file can provide the required surface.
- Exit condition: core builds in UE 5.3.2 without pulling unrelated handlers.

### 4. Complete Blueprint Support

- Preserve current `read_blueprint`, graph inspection, dependency inspection,
  compile, and validation behavior.
- Add supported variable, component, function, macro, and interface actions in
  small groups.
- Gate or adapt SubobjectDataSubsystem, user-defined type, and property editing
  paths based on UE 5.3 APIs.
- Validate parameter names against `src/tools/blueprint.ts` after every group.
- Exit condition: all portable Blueprint actions have live read coverage and
  test-project mutation coverage.

### 5. Restore General Editor and Asset Actions

- Bring back project status, discovery, asset listing, metadata, dependency,
  and non-destructive asset inspection first.
- Adapt asset creation, import, property, mesh, and bulk-edit handlers one
  family at a time.
- Isolate Geometry Script and editor API differences behind explicit gates.
- Exit condition: each asset action is either verified or classified.

### 6. Restore Level and World Actions

- Port world querying, actor inspection, level listing, and transform reads.
- Add actor, component, level, landscape, foliage, and water mutations only in
  the test project with rollback-aware tests.
- Keep unavailable module references dynamic and return clear availability
  errors.
- Exit condition: all applicable level actions have safe test coverage.

### 7. Restore Blueprint-Adjacent Systems

- Port widget, animation, Control Rig, gameplay, input, GAS, networking, and
  StateTree handlers according to the matrix.
- Treat engine plugins such as GameplayAbilities and Enhanced Input as optional
  dependencies with actionable errors when disabled.
- Exit condition: every portable action from these categories is verified or
  explicitly deferred with an engine reason.

### 8. Restore Content Authoring Systems

- Port materials, Niagara, audio, PCG, sequencer, mass, chooser, and related
  handlers by dependency group.
- Start with read and enumeration actions, then creation, then property and
  graph mutations.
- Do not add dependencies for UE 5.4-only systems that have no UE 5.3
  equivalent.
- Exit condition: each category has a supported action set and an explicit
  unavailable-action list.

### 9. Registration and Schema Parity

- Make TypeScript tool schemas advertise only the actions registered by the
  active engine version.
- Add startup reporting that identifies the engine version and compatibility
  surface.
- Verify every advertised action returns a handler result, not `Unknown method`.
- Exit condition: tool discovery and bridge registration agree exactly.

### 10. Automated Verification

- Add an engine-free matrix test that detects registration and schema drift.
- Add UE 5.3 compile checks for the compatibility module.
- Run focused read-only live tests against VELUX after confirming its target.
- Configure a UE 5.3 test project before running destructive smoke tests.
- Exit condition: supported actions have an appropriate automated check.

### 11. Documentation and Handoff

- Document the UE 5.3 support boundary, required project plugins, build steps,
  and the supported action matrix.
- Keep the matrix current as actions move from adapted to verified.
- Record unresolved UE 5.3 limitations separately from implementation work.
- Exit condition: another developer can reproduce the build and determine
  support status without source archaeology.
